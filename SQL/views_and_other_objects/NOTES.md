# Views and Other Database Objects - Notes

## 1. Simple vs. Complex Views & DML Restrictions
- **Definition of View**: A virtual or logical table based on an underlying `SELECT` query. It does not store physical data blocks; data is queried dynamically from underlying base tables.
- **Classification**:
  | Feature | Simple View | Complex View |
  | :--- | :--- | :--- |
  | **Base Tables** | Exactly 1 table | 1 or more tables (joins) |
  | **Group Functions** | None | Contains `SUM`, `AVG`, `MAX`, `MIN`, `COUNT`, etc. |
  | **`GROUP BY` / `DISTINCT`** | None | Allowed |
  | **DML Operations** | Permitted (directly modifies base table) | Heavily restricted or forbidden |
- **Strict DML Prohibition**:
  - DML (`INSERT`, `UPDATE`, `DELETE`) is **strictly forbidden** on views containing:
    1. Group functions
    2. `GROUP BY` clause
    3. `DISTINCT` keyword
  - Violation error:
    `data manipulation operation not legal on this view`.

## 2. View Integrity Clauses (WITH READ ONLY & WITH CHECK OPTION)
- **`WITH READ ONLY`**:
  - Enforces strict read-only access.
  - Any attempt to run `INSERT`, `UPDATE`, or `DELETE` through the view fails with:
    `cannot perform a DML operation on a read-only view`.
- **`WITH CHECK OPTION`**:
  - Permits DML but ensures that all inserted or modified rows **satisfy the view's WHERE clause condition**.
  - Prevents rows from falling outside the scope of the view after an update/insert.
  - Attempting to insert or update a row that violates the view's `WHERE` clause fails with:
    `view WITH CHECK OPTION where-clause violation`.

## 3. Database Sequences
- **Purpose**: Independent database object used to automatically generate unique integer numbers (typically surrogate primary keys).
- **Key Parameters**:
  - `START WITH <n>`: Initial value to generate.
  - `INCREMENT BY <n>`: Step interval.
  - `CACHE <n>` vs. `NOCACHE`: Pre-loads `<n>` values in memory for high-speed retrieval. Default is 20.
  - `NOCYCLE` vs. `CYCLE`: Halts at `MAXVALUE` (default, throws error) vs. wraps around to `MINVALUE`.
- **Pseudocolumns**:
  - `NEXTVAL`: Advances the sequence and returns the next value.
  - `CURRVAL`: Returns the current value generated by `NEXTVAL` in the **active session**.
- **The Session Initialization Trap**:
  - In a new session, referencing `CURRVAL` before invoking `NEXTVAL` at least once raises:
    `sequence CURRVAL is not yet defined in this session`.
- **Why Gaps Occur (Sequences are not contiguous)**:
  - Sequences guarantee uniqueness, never gap-free consecutive numbers.
  - Common gap causes:
    1. **Rollback**: Fetching `NEXTVAL` and rolling back does not return the number to the sequence.
    2. **Database Restart / Crash**: Unused sequence numbers cached in memory (`CACHE`) are lost.
    3. **Multiple Tables**: Using the same sequence across different tables.

## 4. Database Indexes & Index Suppression
- **Purpose**: Schema objects that speed up data retrieval by providing direct pointers to row locations (ROWID), reducing disk I/O.
- **Index Types**:
  - **B-Tree Index (Default)**:
    - Ideal for **high-cardinality** columns (columns with many unique values, e.g., `employee_id`, `email`, `last_name`).
    - Standard tree structure (Root, Branches, Leaves).
  - **Bitmap Index**:
    - Ideal for **low-cardinality** columns (columns with few distinct values, e.g., `gender`, `marital_status`, `status`).
    - Great for read-heavy Data Warehouses; strictly avoided in OLTP because row updates lock the whole bitmap index segment.
- **Index Suppression by Functions (Exam Trap)**:
  - If a function or calculation is applied to an indexed column in the `WHERE` clause (e.g., `WHERE TO_CHAR(hire_date, 'YYYY') = '2020'` or `WHERE UPPER(col) = 'VAL'`), Oracle **cannot use the standard B-Tree index** and falls back to a **Full Table Scan (FTS)**.
  - **Remedy**: Create a **Function-Based Index** matching the exact expression:
    `CREATE INDEX idx_emp_hire_yr ON employees(TO_CHAR(hire_date, 'YYYY'));`

## 5. Database Synonyms & Name Resolution Order
- **Purpose**: An alias or alternate name for an underlying database object (table, view, sequence, procedure, package).
  - Masks physical location and schema owner.
  - Simplifies query statements by removing schema qualifiers (`hr.`).
  - **Security Rule**: Synonyms do **not** grant permissions; privileges must still be explicitly granted on the underlying object.
- **Types**:
  - **Private Synonym**: Visible and accessible strictly within the creator's schema (`CREATE SYNONYM syn_name FOR schema.object;`).
  - **Public Synonym**: Accessible to all database users (`CREATE PUBLIC SYNONYM syn_name FOR schema.object;`).
- **Oracle Object Name Resolution Order**:
  When an unqualified object name is queried (e.g., `SELECT * FROM table_name`), Oracle searches in this exact order:
  1. **Local Object**: An object directly owned by the querying user in their schema.
  2. **Private Synonym**: A private synonym defined in the user's schema.
  3. **Public Synonym**: A database-wide public synonym.
  4. If not resolved: `table or view does not exist`.
